KafkaversusRabbitMQ

Both put a buffer between services, so a slow or dead service never blocks the one calling it. RabbitMQ delivers a message and forgets it. Kafka writes it down and lets every reader keep its own bookmark.

RabbitMQ is a postmanSmart broker, simple consumers. The message flows through, then it’s gone.
Kafka is a diarySimple broker, smart consumers. The message lives in the log; readers track their page (offset).

Why a queue at all? A direct HTTP call from the order service to the inventory service stalls, times out or drops requests when inventory is slow, down or flooded. A queue absorbs the spike (a flash sale, say) and lets the consumer work at its own pace.

One difference drives everything: RabbitMQ deletes on consume, Kafka keeps.

Ordering

RabbitMQ is FIFO per queue, but parallel consumers break the order. Kafka keeps order only inside a partition, so you pick the key that matters.

Partition 0cust 12345 #1cust 12345 #2cust 12345 #3
Partition 1cust 67890 #1cust 55501 #1cust 67890 #2
Key = customerId. Each customer’s orders stay in sequence; partitions run in parallel; no global order.

Trade-off: RabbitMQ gives global order with one consumer. Kafka gives per-entity order with parallelism.

Delivery guarantees

When a consumer fails, you either lose the message or deliver it again.

At-most-once

Risk: lost messages

Send once, never retry. Fast. Both support it.

At-least-once

Risk: duplicates

Retry until acked. No loss. The industry default; both support it.

Exactly-once

Kafka only, narrow

Only Kafka topic to Kafka topic, one cluster, with transactions.

The moment you write to a database, call an API or cross clusters, you’re back to at-least-once. So make consumers idempotent: processing the same message twice must be harmless.
@KafkaListener(topics = "orders")
void handle(OrderEvent e) {
  if (processedRepo.existsById(e.eventId())) return; // seen it, skip
  inventory.reserve(e);
  processedRepo.save(new Processed(e.eventId()));    // same DB transaction ideally
}

When to use which

A job to do once goes to RabbitMQ. A fact others may care about, now or later, goes to Kafka.

RabbitMQ

  • Task queues, background jobs: emails, payments, image resizing
  • Smart routing: the broker picks the worker by content
  • Sub-5 ms delivery at moderate scale
  • Small team, simple operations
Instagram (photo upload processing), Reddit (comment threads, karma)

Kafka

  • Many systems reading the same events: analytics, fraud, billing, audit
  • Replay to debug or rebuild state
  • Millions of events per second
  • A permanent event history
LinkedIn (invented it), Netflix (recommendations, billing), Uber (pricing, fraud)

Or both

Kafka is the event backbone; RabbitMQ runs the jobs those events trigger.

In the interview

Name the need first, then the tool. “I’ll add Kafka” without a reason is a red flag.

“Checkout shouldn’t wait on inventory, so I’ll decouple with a queue. Order events are read by inventory, analytics and notifications, and we may want replay, so I’d use Kafka, partitioned by orderId. Side jobs like emails go to a RabbitMQ task queue. Delivery is at-least-once, so consumers are idempotent on eventId.”
  • Trap: “Kafka’s exactly-once removes duplicates.” Not once a database or external API is involved.
  • Trap: “Kafka keeps messages in order.” Only per partition.
  • Trap: Kafka for a simple email job. Over-engineering; a task queue is enough.

Likely follow-ups

How do you keep one user’s events in order?

Use userId as the partition key. All their events land in one partition, which is ordered.

A consumer crashed mid-message. Now what?

No ack or no offset commit, so the message is redelivered (at-least-once). The consumer must be idempotent.

A message keeps failing.

RabbitMQ moves it to a dead letter queue. In Kafka, send it to a retry topic, then a dead-letter topic (Spring Kafka has a recoverer for this).

How do you scale Kafka consumers?

Add consumers to the same group. Parallelism caps at the number of partitions; extra consumers sit idle.

The queue keeps growing.

Watch consumer lag, add workers, apply backpressure or rate limits upstream.

Why not a direct HTTP call?

Coupling. A slow or down service stalls the caller, and a spike drops requests with nowhere to buffer them.

At work

Map each async flow to job or fact. These also make good “tell me about a system you built” stories.

Job shaped

Repurposer’s heavy wizard steps

Transcribe, clip, render: each is one unit of work done once. Laravel queues (Redis driver) already fit this model. Reach for RabbitMQ when you need routing or priorities across many worker types, or workers in another language such as Java or Python.

Fact shaped

Webinar tool’s live comments

Comments from YouTube, Instagram and Facebook are events that several readers want: the live display, moderation, post-webinar analytics. That’s the Kafka shape (one stream, independent consumer groups, replay). At your scale, Redis Streams gives the same model with far less to run.
